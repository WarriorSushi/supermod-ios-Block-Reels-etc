## Local source findings

- `EntitlementStore.refresh()` originally rejected verified current subscription entitlements whose billing-period expiration was in the past. This can exclude subscribers during an active billing grace period. The correction retains known-product/revocation/upgrade guards and uses verified renewal grace metadata for refresh timing. Verified terminal subscription status takes precedence over a stale current-entitlement entry. A missing renewal deadline causes a bounded 60-second recheck rather than a busy loop. Apple's `Transaction.currentEntitlements` includes both subscribed and grace-period states. Source: [currentEntitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements).
- `Supermod.storekit` subscription descriptions now mention Instagram, Facebook and YouTube. Product IDs and prices are unchanged.
- The existing store uses verified transactions, limits access to known product IDs, handles pending/cancel/error outcomes, exposes restore, listens for transaction updates, refreshes on foregrounding, and rejects revoked/upgraded transactions. These are source observations, not production transaction validation.
- `PrivacyInfo.xcprivacy` is included in the app resource phase. It declares app-local UserDefaults (`CA92.1`) and uptime (`35F9.1`) corresponding to preferences and foreground usage accounting. No external analytics SDK, Screen Time/Family Controls extension, custom browser engine entitlement or capability entitlement file was found. The present in-app quiet-hours feature does not establish system-wide blocking. Manifest review must still be completed against the distribution archive and actual service behavior. Source: [Required-reason API declarations](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api).
- Privacy/support publishing cannot be honestly completed by inventing a contact address, pointing to the unrelated website, or silently changing that production site. Those external dependencies remain explicit.

## Verification boundaries

The final StoreKit regression enters an actual verified local `.inGracePeriod` and confirms access. It then refunds the failed renewal attempt and verifies that the signed subscription status is revoked despite a stale entry remaining in `currentEntitlements`. The app must revoke access in this state. Finally it refunds the original paid transaction, explicitly confirms that StoreKit returns no current Supermod entitlements, and confirms the app remains locked. The existing purchase/restore/refund test remains in the focused suite.

`Entitlement-stale-red.xcresult` demonstrated the defect before the terminal-status fix: “Verified revocation must override a stale current entitlement” failed, while the StoreKit-state preconditions passed. Earlier `Entitlement-characterization.xcresult` passed with the original expiration filter, but that pass masked the stale-entry behavior and is superseded. Xcode's initial grace transaction uses a future extended expiry, so the past-paid-expiration grace edge is still based on Apple's documented contract rather than a faithful local reproduction.

The focused post-fix run passed both StoreKit tests: `Evidence/RC-2026-11-11/Entitlement-stale-green.xcresult` (matching `.log`, process exit 0). The integrated RC test run exposed the incorrect refund assumption and was not accepted as a green release check. The subsequent integrated rerun is recorded in the current RC handoff; earlier failed bundles remain as diagnostic evidence.

This release audit did not sign in to social accounts, inspect private messages, enable production billing grace periods, perform a transaction outside Xcode's local StoreKit environment, or test distribution delivery. The broader RC task owns live browsing, physical-device smoke tests and accessibility evidence. Historical checks in `docs/verification.md` are context rather than new acceptance results.
